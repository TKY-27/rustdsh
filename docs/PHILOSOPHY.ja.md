# 設計思想: Node.js という巨人を手懐ける Rust の手綱

`rdsh` は DeepSeek Harness を置き換えるものではありません。巨人に手綱をかける道具です。
Node.js には得意な処理をそのまま任せ、その周りにある小さく遅延に敏感な境界だけを Rust で書きます。

この文書では、なぜハイブリッド構成なのか、境界をどこに引くのか、そして何をあえてやらないのかを説明します。
出来上がった構成の分担は [ARCHITECTURE.md](ARCHITECTURE.md)、実測値は [BENCHMARKS.md](BENCHMARKS.md) にあります。

## 巨人の正体

Node.js と V8 があるから Harness はこれだけ多機能でいられます。エージェントループ、プロファイル起動、
モデル接続、MCP ツール、Web UI はすべて上流ランタイムが持つ機能です。これを Rust で作り直すと、
上流の変更をすべて手作業で追うことになり、ずれた時点で互換性を失います。そもそもそこはボトルネックではないので、
そのままにします。

コストが出るのは境界です。プロセスの起動と、小さな確認のたびに起動し直すこと。ここでは3つの性質が効いてきます。

## 境界にある3つの弱点

1. **起動が重い。** 冷えた Node.js プロセスは、仕事を始める前にインタプリタの起動とモジュール読み込みを払います。
   `dsh --version` は約88 ms、最大RSSは約66 MBです。1回のコマンドなら問題になりませんが、すべての呼び出しを
   包む CLI では「一瞬」と「待たされる」の差になります。
2. **頻繁なフックはプロセス起動と相性が悪い。** PreToolUse フックはツール呼び出しごとに1回走ります。そのたびに
   Node.js の判定プロセスを起動すると、起動コストがツール呼び出し回数だけ積み上がり、フックは方針チェックではなく
   セッション最大の固定費になります。切ろうと思われない程度に安い必要があります。
3. **外部ツール実行には関所が要る。** モデルが実行を求めたコマンドは、1か所で検査して拒否できる必要があります
   （`rdsh guard`）。この場所はすべてのツール呼び出しの経路にあるため、速く、かつ監査できる大きさでなければ
   なりません。

## 手綱

方針は「速さが要る経路だけを移植し、それ以外は委譲する」です。遅延と安全を決める境界は Rust が持ちます。

- PreToolUse フック（`rdsh guard`）。オプトインの構造化ファイルポリシーを含みます。
- Node.js を起動する意味がないローカル高速処理。トークン見積り、検索、セッション一覧と圧縮、依存関係の検査、
  環境診断。

エージェントランタイム全体が要る処理は Node.js に残し、そのままの `exec` で到達します。会話ループ、
プロファイル起動、モデル実行、MCP ツール、Web UI です。委譲は構造上バイト単位で同一なので、手綱が巨人の動作を
変えることはありません。変わるのは操るコストだけです。

## アーキテクチャ

```text
            user / CLI
                |
                v
      +-------------------+          the reins
      |   rdsh  (Rust)    |          fast, memory-safe, auditable
      +---------+---------+
                |
     every tool call         local fast paths
                +-----------------------> guard, tokens, search, sessions
                |
                |  only when the work needs the full agent runtime
                v
      +-------------------+          the titan
      | DeepSeek Harness  |          session loop, models, MCP, Web UI
      | Core  (Node.js)   |
      +-------------------+
```

上の経路はツール呼び出しのたびに通り、Node.js を起動しません。下の経路はエージェントランタイム全体で、
本当に必要なときだけ入り、上流実装をそのまま動かします。

## 境界のコスト（実測）

数値はすべて Linux x86_64 の1ホスト、`n=15` のプロセス単位の実測です。
[BENCHMARKS.md](BENCHMARKS.md) に記録があり、`scripts/benchmark-node-vs-rust.py`
（Node.js 側は `scripts/benchmark-node-reference.mjs`）で再測定できます。絶対値はホストに依存します。

| 境界の処理 | rdsh (Rust) | Node.js の比較対象 | 差 |
| --- | --- | --- | --- |
| `rdsh --version` プロセス起動（起動のみ） | 約0.90 ms | 本家 `dsh --version` 約88 ms | 約98倍 |
| PreToolUse フック `rdsh guard`、1ツール呼び出し（起動込み） | 約2.0 ms | 等価な Node.js 判定スクリプト 76〜84 ms | 約40倍 |
| PreToolUse フックの最大RSS | 5.9 MiB | 49.6 MiB | 約1/8 |

注意が2つあります。1つ目は、`約0.90 ms` は `rdsh --version` の**プロセス起動のみ**の値で、
フックの評価時間ではありません。フックの値は起動込みであり、ツール呼び出し1回あたりの判断にはこちらを使います。
2つ目は、フック・`tokens`・`search` の比較対象は等価な Node.js 実装であり、本家 `dsh` ではありません。
本家に該当するサブコマンドがなく、本家との倍率は主張しません。

プロファイルを起動したセッションはこの数値の対象外です。`rdsh` はプロファイル起動時に同じ上流 Node.js の
`dsh` を `exec` するため、会話の起動時間・対話速度・メモリは上流と同等です。

## Non-goals（やらないこと）

境界は意図的に狭くし、そのままにします。[ROADMAP.md](ROADMAP.md) の方針どおりです。

- エージェントループやプロファイル起動を Rust で再実装しない。
- Harness の UI やプロトコルを fork しない。
- Rust 自体を目的にしない。境界にない経路は Node.js と上流に残す。
